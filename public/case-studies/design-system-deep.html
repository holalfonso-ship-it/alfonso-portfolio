01

An app for two reading directions, one designer.

AI Cleaner is an iOS app that helps people free up storage on their phone. It launched in the US and in Arabic-speaking countries, so every screen had to work in two reading directions, not just two languages.

I was the only designer and I led design end to end: the design system, the app layouts, the wireframes for each feature, the branding, and the technical solution for RTL. I worked with the product managers and the iOS developers. The developers who reviewed the Arabic version were Arabic speakers themselves, so they checked the RTL variants directly.

The real problem

"Mirroring the screen isn't enough. In Arabic, text length reshapes the layout, and some icons change meaning by direction, not just position."

The app had to feel native in two reading directions. Text length changes the layout, Arabic and Latin brand names share the same line, navigation arrows and icons flip, and some icons change orientation entirely, like PLAY and VOLUME. Branding elements are the one thing that never mirrors.

02

One component library, not two.

Every component with text or navigation has an RTL = True/False property. I built the variants by hand with help from the RTL Language plugin, which mirrors the component, translates the text into Arabic, and creates the variant inside the same component.

01

RTL as a variant inside each component, not as a separate mode

I chose variants over Variable modes because the system was scaling up from a simple UI kit and I wanted to move fast. I also considered designing the Arabic layouts separately, without RTL variants inside the components, and discarded that: I wanted every component in one place, as a single source of truth, not two libraries that could drift apart.

The trade-off: maintaining the variants by hand costs more than an automated mode would. In return, I can see in one place, in the same component, exactly how it's assembled in both directions.
02

Tokens are shared, direction lives in the components

One Variables collection holds colors, spacing, typography and radius, with Light and Dark as modes of the same variables, not separate ones. RTL doesn't touch the tokens at all: it's a component-level property, so both directions draw from the same source of truth for color and spacing.

03

Handoff: both directions, side by side

Developers received an Arabic-specific layout, built with the same components in their RTL variant, right next to the LTR layout, so they could compare both versions directly rather than reconstructing the Arabic layout from specs alone.

03

Anatomy of a component: Button Google.

Five states, normal, hover, pressed, disable, and focus, each with an LTR and an RTL variant inside the same component. It's a small component that shows what RTL actually requires.

Mirrors

The icon position and the text alignment flip. Navigation arrows and directional icons follow the same rule everywhere in the system.

Adapts

The width changes, 179px → 208px, because the Arabic text is longer, not because of a design decision. Auto Layout handles it. The Latin brand name "Google" stays inside the same line as the Arabic text.

Stays the same

The radius (Pill, 100) and the color variables, Background/Primary, Background/Secondary, Separator/Opaque, Label/Secondary, are identical in both directions.

04

213 components, one token collection.

Almost every component that has text or navigation elements carries an RTL variant. Icon orientation is part of the same system: PLAY and VOLUME change orientation by direction, the way an arrow does.

07

What I'd do differently.

01

Document the system properly, not just in Figma

I relied on Figma annotations for handoff, and it worked, but it meant the reasoning behind decisions lived in my head more than in the file. I'd document the system properly from the start: not just what a component is, but why it exists and when to use it.

02

Maintaining RTL variants by hand costs more than it should

Building the RTL variants by hand, with the plugin's help, costs more to maintain than an automated approach would. In return, I could see in one place how components and layouts were assembled in both directions, which mattered while the system was still taking shape. At this scale, I'd look again at Variable modes for direction.

08

Toward an agentic design system: Aida.

AI Cleaner taught me how to make one system hold two reading directions without splitting into two products. Aida is my own research project, asking the next question: what does a design system need so that people and AI agents can both use it, without the agent inventing a component that already exists?

Layer 1
Component metadata
Props, tokens, when to use it, accessibility notes, and a link back to the Figma source.
Layer 2
Generated index
A machine-readable index of every component, kept in sync with the metadata.
Layer 3
Protocol for agents
A CLAUDE.md file that tells an agent to extend an existing component before creating a new one, with a checklist, an ARC working cycle, and a flags log.
Layer 4
Storybook
A public showcase that consumes the same metadata people and agents both read from.

Where it stands: phases 0 to 3 are done, phase 4 is in progress, with 11 components live today. It's a solo research project, and it doesn't have impact metrics yet, this is early, honest work in progress, not a finished system.
